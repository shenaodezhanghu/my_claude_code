# 第三章 设计 Coding Agent 系统提示词

> 当前代码进度：`myclaude/mycode/mini_claude/prompt.py` 尚未完成，`agent.py` 仍使用内联 `SYSTEM_PROMPT`。本章是第二章之后的下一步，不代表这些代码已经接入当前 Agent。

工具决定 Agent 能做什么，系统提示词决定 Agent 如何使用这些工具。本章将把简单的一句角色说明，升级为由静态规则和动态环境共同组成的 Coding Agent 提示词。

## 3.1 本章目标

<strong>（1）理解系统提示词不是“人设文案”，而是运行契约</strong>。

<strong>（2）区分静态核心与动态环境信息</strong>。

<strong>（3）让 Agent 先检查、再修改、最后验证</strong>。

## 3.2 提示词结构

```text
系统提示词
├── 身份与目标
├── 工具使用规则
├── 编辑工作流
├── 安全约束
├── 沟通方式
└── 当前环境（目录、平台、项目说明）
```

前五部分基本稳定，可以视为静态核心；当前目录和项目指令会变化，应在每轮调用前动态构建。

### 3.2.1 为什么拆成静态核心和动态环境

静态核心跨会话基本不变：

```text
身份
工具使用原则
编辑工作流
安全边界
沟通规则
```

动态环境每次启动甚至每轮都可能改变：

```text
操作系统
当前工作目录
Git 分支和状态
项目 CLAUDE.md / AGENTS.md
当前可用的延迟工具
```

把两者分开，不只是为了代码整洁。稳定内容更适合后续做 Prompt 缓存，动态事实也不会被写死在旧字符串中。

## 3.3 实现静态核心

创建 `mini_claude/prompt.py`：

```python
from pathlib import Path
import platform


STATIC_PROMPT = """你是一个运行在用户项目中的编程智能体。

你的目标是准确、安全地完成用户交给你的软件任务。

工作规则：
1. 不要猜测文件内容；需要时先使用工具读取。
2. 修改前先理解相关代码和现有风格。
3. 优先进行范围最小、可验证的修改。
4. 工具失败时阅读错误，修正参数后再尝试。
5. 修改完成后使用适当方式验证结果。
6. 不要声称执行了实际上没有执行的操作。
7. 不泄露 API Key、口令或其他秘密信息。

沟通规则：
- 回答简洁明确。
- 说明最终结果和验证情况。
- 遇到无法安全推断的重要选择时，向用户说明。
"""


def build_system_prompt() -> str:
    cwd = Path.cwd()
    project_instruction = load_project_instruction(cwd)

    environment = f"""
当前环境：
- 操作系统：{platform.system()}
- 当前工作目录：{cwd}
"""

    if project_instruction:
        environment += f"\n项目说明：\n{project_instruction}\n"

    return STATIC_PROMPT + environment


def load_project_instruction(cwd: Path) -> str:
    for name in ("CLAUDE.md", "AGENTS.md"):
        path = cwd / name
        if path.exists():
            return path.read_text(encoding="utf-8")
    return ""
```

静态提示词中最重要的不是“你是一名优秀程序员”之类的人设，而是可以直接指导行为的规则。例如：

```text
不确定文件内容 → read_file
不知道文件位置 → list_files / grep_search
修改已有文件 → 先读，再用 edit_file
工具失败 → 根据错误修正参数，不要假装成功
修改完成 → 运行相关测试或检查
```

这种工具偏好映射能减少模型用 `run_shell` 绕过专用工具，也能让执行轨迹更容易观察和限制。

### 3.3.1 加入 Git 动态信息

可以用标准库读取简要 Git 状态：

```python
import subprocess


def get_git_context() -> str:
    try:
        branch = subprocess.run(
            ["git", "branch", "--show-current"],
            capture_output=True,
            text=True,
            timeout=3,
        ).stdout.strip()
        status = subprocess.run(
            ["git", "status", "--short"],
            capture_output=True,
            text=True,
            timeout=3,
        ).stdout.strip()
        return f"- Git 分支：{branch or '(detached)'}\n- Git 状态：\n{status or '(clean)'}"
    except (OSError, subprocess.SubprocessError):
        return "- Git：当前目录不是可读取的 Git 仓库"
```

再将它加入 `environment`。Git 状态只是提供事实，不应让 Agent 自动提交或覆盖用户已有修改。

## 3.4 接入 Agent Loop

在 `agent.py` 中导入：

```python
from mini_claude.prompt import build_system_prompt
```

然后在模型请求中增加：

```python
response = self.client.chat.completions.create(
    model=self.model,
    messages=[
        {"role": "system", "content": build_system_prompt()},
        *self.messages,
    ],
    tools=self.tools.schemas(),
)
```

不要把 system 消息永久重复追加到 `self.messages`。动态提示词可以在每次请求时临时组合，这样当前目录或项目说明发生变化后能够及时更新。

这也避免每轮执行下面这种错误操作：

```python
# 错误：每轮都会把 system 再追加一次
self.messages.append({"role": "system", "content": build_system_prompt()})
```

正确方式是请求时临时拼接：

```python
request_messages = [
    {"role": "system", "content": build_system_prompt()},
    *self.messages,
]
```

## 3.5 项目指令的作用

在练习目录创建 `AGENTS.md`：

```markdown
# 项目约定

- Python 文件使用类型标注。
- 新增功能必须附带测试。
- 不允许修改 fixtures 目录中的样例数据。
```

然后要求 Agent 新增一个函数，观察它是否遵循约定。项目指令属于用户提供的上下文，但真正危险的行为仍应由程序权限系统拦截，不能只依赖提示词。

项目指令的优先用途是保存仓库特有事实，例如测试命令、代码风格和禁止修改的目录。不要把 API Key 或密码写进项目指令，因为其内容会发送给模型。

### 3.5.1 向上查找项目指令

Agent 可能从项目子目录启动，因此只检查 `Path.cwd() / "AGENTS.md"` 容易漏掉仓库根目录的说明。可以从当前目录逐级向上寻找：

```python
def find_project_instruction(start: Path) -> Path | None:
    for directory in (start, *start.parents):
        for name in ("CLAUDE.md", "AGENTS.md"):
            candidate = directory / name
            if candidate.exists():
                return candidate
    return None
```

教学版先加载最近的一份即可；如果以后要支持多层规则，需要明确合并顺序和冲突优先级。

### 3.5.2 未来 deferred tools 如何进入提示词

第二章当前没有实现延迟工具。未来确实加入 deferred tools 后，系统提示词只需提供简短名称，并告诉模型需要时使用 `tool_search`：

```python
deferred_names = get_deferred_tool_names()
if deferred_names:
    environment += (
        "\n可按需搜索的工具："
        + ", ".join(deferred_names)
        + "。需要时先调用 tool_search。\n"
    )
```

这样既让模型知道能力存在，又不必每轮支付完整参数 Schema 的 Token 成本。当前阶段不要加入这段代码，因为 `get_deferred_tool_names()` 尚不存在。

## 3.6 提示词设计的常见误区

<strong>提示词越长越好：</strong>错误。重复、冲突的规则会降低模型抓住重点的能力。

<strong>只写“你是优秀程序员”：</strong>这没有定义可执行工作流。应该明确何时读文件、何时验证、失败后怎么办。

<strong>用提示词代替权限系统：</strong>提示词只能引导模型，无法构成可靠安全边界。

<strong>把环境写死：</strong>目录和项目说明应动态生成，不应复制进固定字符串。

<strong>在 System Prompt 中重新抄写所有工具 Schema：</strong>API 的 `tools` 参数已经负责描述工具。System Prompt 只需规定选择策略和边界，重复 Schema 会浪费 Token，并可能产生不一致。

<strong>用提示词修复代码错误：</strong>如果模型收到的用户消息为空、工具 Schema 格式错误或工作目录不对，增加“必须调用工具”只能掩盖根因。先检查实际请求，再调整提示词。

## 3.7 本章练习

1. 增加当前时间、Python 版本等环境信息，并思考哪些信息真正有用。
2. 创建一条互相冲突的项目规则，观察模型如何处理，再消除冲突。
3. 让 Agent 修改代码并验证，记录它是否遵循“先读后改”。
4. 尝试删掉工具描述，只保留工具名，观察工具选择质量变化。

## 3.8 本章小结

本章建立了 Coding Agent 的行为框架。系统提示词负责指导模型采用可靠的软件工作流，动态环境负责告诉模型它当前身处何处。下一章将为它增加真正可持续使用的命令行交互和会话保存。
